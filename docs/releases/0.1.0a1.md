# Better Hermes Hindsight 0.1.0a1

`0.1.0a1` is the first development prerelease candidate of the unofficial `better_hindsight`
provider. It targets unmodified current stable Hermes and an external/self-hosted Hindsight 0.8.5
service. It is not approved for production use.

## What this candidate proves

- Current-query recall runs before the first model call and fails open on remote errors.
- Completed supported turns can be redacted, admitted locally within strict row/byte bounds, and sent
  asynchronously with stable replace-mode replay.
- Multi-segment retained sources preserve enough non-sensitive metadata for remote reconstruction.
- Hermes owns Git-plugin installation; `uv` owns the wheel and exact Hindsight client transition.
- One isolated synthetic proof demonstrated useful recall, source preservation, wheel attestation,
  and complete generated-bank cleanup.

## Limitations

- External/self-hosted Hindsight **0.8.5 only**; newer Hindsight versions are outside the tested
  contract.
- One static bank for one explicitly asserted principal; there is no multi-user bank router.
- Automatic retention is disabled by default and must remain off until an operator completes a
  separately authorized isolated canary.
- `codex_app_server`, Windows sender election, cloud Hindsight, embedded-daemon management,
  production migration, automatic pruning, and automatic rollback are unsupported.
- Better requires `hindsight-client==0.8.5`, while bundled Hindsight requires `0.6.1`; changing
  providers in one interpreter is a stopped-process package transition, not a configuration-only
  switch.

## Rollback

Follow [docs/rollback.md](../rollback.md). Stop every process sharing the Hermes interpreter, restore
the SDK required by the selected provider with `uv`, select the bundled provider, remove the
host-managed Better plugin only after provider selection is safe, and restart. Preserve both
Hindsight banks and Better's local outbox; rollback does not migrate, drain, prune, or delete them.

## Publication boundary

The repository workflow builds only an exact manually selected prerelease tag whose full commit SHA
matches the operator input. PyPI publication additionally requires `publish_pypi=true`, an
operator-protected `pypi` environment, trusted-publishing OIDC, and the
`PYPI_RELEASE_CONFIGURED=true` repository variable set only after those remote protections exist. The
current private repository has neither that environment nor the variable, so a publication request
fails closed. Creating or pushing the tag, making the repository public, running the publication job,
activating a canary, or changing production remains separately authorized.
